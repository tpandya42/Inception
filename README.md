# Inception

## Description

This project is about setting up a small infrastructure composed of different services using Docker. The goal is to virtualize several Docker images, creating them in a personal virtual machine. This project aims to broaden knowledge of system administration by using Docker.

The infrastructure consists of the following services, each running in a dedicated container:
-   **NGINX:** A web server with TLSv1.2/TLSv1.3 enabled, serving as the main entrypoint to the application.
-   **WordPress:** A content management system with `php-fpm`.
-   **MariaDB:** A relational database for WordPress.

All services are connected via a dedicated Docker network. The data for WordPress and MariaDB is persisted using Docker volumes.

## Project Description

### Docker and Design Choices

This project leverages Docker to containerize each part of the application stack, ensuring a consistent and isolated environment for each service. The main design choices include:

*   **Service-specific Dockerfiles:** Each service (NGINX, WordPress, MariaDB) has its own Dockerfile, built from a `Debian` base image. This allows for fine-grained control over the configuration of each service.
*   **Docker Compose:** The `docker-compose.yml` file is used to orchestrate the multi-container application, defining the services, networks, and volumes.
*   **Makefile:** A `Makefile` at the root of the repository simplifies the setup and management of the application, with commands to build and run the Docker containers.
*   **Environment Variables:** A `.env` file is used to store sensitive information like database credentials and domain names, which are then used by the Docker containers.

### Virtual Machines vs Docker

-   **Virtual Machines (VMs)** virtualize the hardware, running a full-fledged guest operating system on top of a host OS. This provides strong isolation but comes with significant overhead in terms of resource consumption (CPU, RAM) and startup time.
-   **Docker** uses containerization, which virtualizes the operating system. Containers are lightweight, isolated processes that share the host's kernel but run in their own user space. This results in much lower overhead, faster startup times, and greater portability compared to VMs.

### Secrets vs Environment Variables

-   **Environment Variables** are a simple way to externalize configuration from the application code. They can be passed to containers at runtime and are easy to manage for development. However, they can be less secure as they might be exposed through logs or container inspection commands.
-   **Docker Secrets** provide a more secure way to manage sensitive data. Secrets are encrypted at rest and in transit, and are only mounted as in-memory files in the containers that need them. This reduces the risk of accidental exposure. The subject strongly recommends using Docker Secrets for production-like environments.

### Docker Network vs Host Network

-   **Host Network:** Using the host network driver (`network_mode: "host"`) makes the container share the networking namespace of the host. The container does not get its own IP address and is not isolated from the host's network. This can be useful for performance, but it sacrifices the security and isolation benefits of containerization.
-   **Docker Network:** Creating a custom bridge network allows containers to communicate with each other by name, while being isolated from external networks. This is the recommended approach for multi-container applications as it provides a clean and secure way to manage inter-service communication.

### Docker Volumes vs Bind Mounts

-   **Bind Mounts** mount a file or directory from the host machine into a container. The path on the host machine is arbitrary and controlled by the user. While useful for development (e.g., mounting source code), they can make the application less portable and can lead to issues with permissions and differences between host and container environments.
-   **Docker Volumes** are managed by Docker and are stored in a dedicated area on the host filesystem. They are the preferred way to persist data generated by and used by Docker containers. Named volumes make it easy to manage the lifecycle of the data independently of the container. This project uses named volumes for the WordPress database and website files, as required by the subject.

## Instructions

1.  **Clone the repository.**
2.  **Navigate to the `srcs` directory and create a `.env` file** from the `env.example` file. Fill in the required environment variables.
3.  **From the root of the project, run the following command:**
    ```bash
    make
    ```
4.  The application will be available at `https://<your-domain-name>.42.fr`.

To stop the application, run:
```bash
make down
```
